Efímero por diseño

Lo que escribes dentro de un contenedor muere con él

Capas de la imagen python:3.11-slimsolo lectura
Tu código y tus archivos de la imagensolo lectura
Capa de escritura del contenedorse borra con docker rm

Todo lo que el proceso escribe dentro va a la capa de abajo. Si borras el contenedor, desaparece.

$ docker run --name efimero python:3.11-slim sh -c "echo dato > /tmp/…
dato
$ docker run --rm python:3.11-slim cat /tmp/nota.txt
cat: /tmp/nota.txt: No such file or directory

Dónde guardar lo que debe sobrevivir

  • Un volumen (siguiente diapositiva).
  • Una carpeta tuya montada en el contenedor.
  • Fuera: una base de datos o un almacén de archivos.

Documentación · sin probar aquí Google documenta que el sistema de archivos de un contenedor en Cloud Run está en memoria y que lo escrito no persiste cuando la instancia se detiene (contrato de contenedores, consultado 10/11/2026). Se comprobará en S3.

Datos que sobreviven

Dos formas de que algo exista fuera del contenedor

Volumen · lo gestiona Docker

-v datos:/datos · sirve para datos que deben sobrevivir (una base de datos, resultados).

$ docker run --rm -v datos:/datos python:3.11-slim cat /datos/nota.txt
version 1

Otro contenedor, distinto, ve el archivo que escribió el anterior.

Carpeta tuya montada

-v "$PWD/modelo-demo:/modelos:ro" · sirve para desarrollo y para cambiar datos o modelo sin reconstruir.

$ …cat /modelos/modelo.txt (tras editar el archivo en tu máquina)
modelo v2
$ …sh -c "echo x > /modelos/otro.txt" (con :ro)
sh: 1: cannot create /modelos/otro.txt: Read-only file system

El proyecto del curso copia el modelo dentro de la imagen (COPY models/…): la imagen es autosuficiente y reproducible. Montarlo sería más flexible, pero depende de que la carpeta esté donde toca.

La pregunta del laboratorio de S2

Dentro del contenedor, el servicio escucha en 0.0.0.0

Escucha en 0.0.0.0 (todas las interfaces)

python -m http.server 8000 con el puerto publicado.

$ curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/
200

Escucha solo en 127.0.0.1

El mismo servidor con --bind 127.0.0.1 y el puerto publicado igual.

$ curl -sS --max-time 3 http://127.0.0.1:8000/
curl: (56) Recv failure: Connection reset by peer

El tráfico entra por la red del contenedor, no por su «127.0.0.1»: un servicio que solo escucha en el bucle local no lo atiende nadie de fuera, aunque el puerto esté publicado. Por eso la API del curso arranca con --host 0.0.0.0.

Documentación · sin probar aquí Cloud Run exige lo mismo: el contenedor debe escuchar en 0.0.0.0 en el puerto al que se envían las peticiones (8080 por defecto) y no en 127.0.0.1 (contrato de contenedores, 10/11/2026).

Para llevarte

Seis ideas que ya puedes usar

1. Imagen ≠ contenedor

La imagen es la plantilla de solo lectura; el contenedor, una ejecución de ella.

2. Vive lo que vive su proceso

Si el proceso termina, el contenedor se para. docker ps -a + docker logs dicen por qué.

3. Lo escrito dentro se pierde

Para que algo sobreviva: volumen, carpeta montada o almacenamiento externo.

4. Hay que publicar el puerto

-p máquina:contenedor. Un puerto de tu máquina, un contenedor.

5. Escucha en 0.0.0.0

En 127.0.0.1 nadie de fuera llega, aunque publiques el puerto.

6. Dentro hay otro Linux

Lo que ves es la imagen, no tu máquina; el núcleo sí es el del anfitrión.
