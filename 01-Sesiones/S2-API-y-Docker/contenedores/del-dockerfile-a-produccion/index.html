La receta de una imagen

Un Dockerfile es una receta: una instrucción, una capa

FROM python:3.11-slim
WORKDIR /app
COPY app.py .
CMD ["python", "app.py"]

El del ejemplo 4: cuatro líneas, una imagen que funciona.

InstrucciónQué haceCuándo
FROMParte de una imagen base: un Debian 13 con Python 3.11al construir
WORKDIRCarpeta de trabajo dentro de la imagen (la crea si no existe)al construir
COPYCopia archivos del contexto (la carpeta del .) a la imagenal construir
CMDEl comando que ejecuta el contenedor al arrancaral arrancar

Otras que verás hoy

RUNEjecuta un comando al construir (pip install)
ENVVariable de entorno con un valor por defecto
USERUsuario con el que corre el proceso
EXPOSEDocumenta el puerto; no lo publica (eso es -p)
HEALTHCHECKCómo comprobar que el contenedor está sano

La imagen es una pila

Cada instrucción añade una capa de solo lectura

docker history saludo:1 (real, de la última a la primera)

CMD ["python" "app.py"]0B
COPY app.py .12.3kB
WORKDIR /app8.19kB
CMD ["python3"]0B
RUN /bin/sh -c set -eux; for src in idle3 p…16.4kB

Dorado: las tuyas · azul: la imagen base (aquí solo se ven sus dos últimas). Las instrucciones que no tocan archivos (CMD) pesan 0 B.

Qué implica

  • Una imagen = una pila de capas; el contenedor añade encima una fina de escritura.
  • Las capas se reutilizan entre imágenes y entre construcciones.
  • Casi todo el peso viene de la base; tus líneas añaden poco.

La regla de oro

Lo que casi nunca cambia, primero; lo que cambia siempre, al final

Orden malo · Dockerfile.malo

FROM + WORKDIRreutilizadas
COPY . .cambia a cada edición
RUN pip install -r requirements.txtse rehace siempre

Orden bueno · Dockerfile.bueno

FROM + WORKDIRreutilizadas
COPY requirements.txt .reutilizada
RUN pip install -r requirements.txtCACHED
COPY app.py .cambia a cada edición

Azul: capa reutilizada · dorado: la capa que cambia · verde discontinuo: se rehace por arrastre.

Docker reutiliza una capa si ella y todas las anteriores no han cambiado; un cambio invalida esa capa y las siguientes. Es lo que hace el Dockerfile del proyecto: primero COPY requirements-api.lock y pip install, y después COPY ia_mlops/ (04-Proyecto-Base/deploy/docker/Dockerfile).

Práctica B · La caché de capas

Construye los dos Dockerfiles, cambia una línea del código y reconstruye. En nuestra ejecución, el orden malo tardó 8.0 s y el bueno 1.2 s (depende de la red y de la máquina: fíjate sobre todo en CACHED).

Terminal del Codespace
cd "$(git rev-parse --show-toplevel)/01-Sesiones/S2-API-y-Docker/contenedores/ejemplos/05-cache"
docker build --progress=plain -f Dockerfile.malo -t cache:malo . 2>&1 | grep -E "\[[0-9]+/[0-9]+\]|CACHED"
echo "# cambio" >> app.py
docker build --progress=plain -f Dockerfile.malo -t cache:malo . 2>&1 | grep -E "\[[0-9]+/[0-9]+\]|CACHED"
docker build --progress=plain -f Dockerfile.bueno -t cache:bueno . 2>&1 | grep -E "\[[0-9]+/[0-9]+\]|CACHED"
echo "# otro cambio" >> app.py
docker build --progress=plain -f Dockerfile.bueno -t cache:bueno . 2>&1 | grep -E "\[[0-9]+/[0-9]+\]|CACHED"

Un archivo de 50 MB que no tiene nada que ver con la aplicación. CONTENT SIZE casi no cambia porque un archivo lleno de ceros se comprime hasta casi nada.

Qué ganas con un buen .dockerignore

  • Imagen más pequeña y construcción más rápida.
  • No filtras secretos: el del proyecto excluye /.env, /*.key y **/credenciales*.json.
  • Tampoco entran .git, data/, notebooks/ ni tests/.

Variables de entorno

La configuración va al arrancar; el secreto, nunca en la imagen

Bien · al arrancar

-e NOMBRE=valor o --env-file archivo: la misma imagen sirve para desarrollo y producción.

$ docker run --rm -e SALUDO="hola desde -e" -e TOKEN_API=abc entorno:1
saludo: hola desde -e
token presente: True
$ docker run --rm --env-file mi.env entorno:1
saludo: desde archivo
token presente: True

Mal · ENV TOKEN_API=… en el Dockerfile

Construye sin error, pero queda grabado en las capas: quien tenga la imagen lo lee.

$ docker build -f Dockerfile.mal -t entorno:mal . 2>&1 | grep Secrets…
#1 WARN: SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ENV "TOKEN_API") (line 6)
 - SecretsUsedInArgOrEnv: Do not use ARG or ENV instructions for sensitive data (ENV "TOKEN_API") (line 6)
$ docker history --no-trunc --format "{{.CreatedBy}}" entorno:mal | g…
ENV TOKEN_API=no-es-un-secreto-real-123

Las claves reales se inyectan desde un gestor de secretos (en GCP, Secret Manager) y llegan al contenedor como variables o archivos al arrancar. Eso se verá en S3. Documentación · sin probar aquí

RoturaSíntomaPrimer comandoTiempo
1. El puerto ya está ocupadoArrancas un segundo contenedor y Docker devuelve un error.docker ps -a --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"5 min
