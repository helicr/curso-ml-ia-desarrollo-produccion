1 · Qué vamos a hacer · Lo que vas a hacer

Siete pasos: de configurar a volver atrás

Los pasos

  1. Preparar la rama y copiar los cuatro workflows
  2. Configurar el repositorio una vez (environment y permiso de PR)
  3. Modo 1: puntuación por lotes con Actions
  4. Modos 2 y 3 y el panel en el Codespace
  5. Nueva versión: igual, rechazada, aceptada, aprobada y publicada
  6. Fusionar el pull request de la referencia
  7. Rollback a la versión anterior

Al terminar sabrás

  • Cuándo conviene lote, bajo demanda u online, y por qué dan lo mismo hasta que llegan datos nuevos.
  • Qué es «el modelo en producción»: una imagen con etiqueta y una ficha en el repositorio.
  • Cómo una puerta de calidad y una aprobación protegen la publicación.
  • Cómo volver atrás sin borrar nada.
Nada se empuja a develop ni a main: se ensaya en ramas lab/… y los cambios entran por pull request.

1 · Qué vamos a hacer · Concepto · una pregunta, un modo

Tres modos de explotación del mismo modelo

ModoLa pregunta del negocioDe dónde salen las 13 variablesCuándo se calculaDónde corre aquí
1 · Lote (batch)«¿A quién llamo hoy?» Se puntúa a todos y se ordenadel pipeline, en el corte del díauna vez al día: schedule 05:17 UTC y Run workflowGitHub Actions: puntuar-lote.yml
2 · Bajo demanda«¿Qué probabilidad tiene el cliente 12670?»leídas de la tabla fs_produccion (ya calculadas, las de ayer)al preguntar, sin cálculo de variablesAPI + interfaz: GET /bajo-demanda/{id} y POST /bajo-demanda
3 · Online«Acaba de comprar: ¿qué le ofrezco ahora?»calculadas al vuelo con el SQL de la capa FS, hasta el instante de la peticiónal preguntar, con los datos frescosAPI + interfaz: GET /online/{id}?corte=

Lote

Barato y programado: una vez al día, para todos los clientes a la vez.

Bajo demanda

Rápido: consulta por clave de variables ya calculadas. No ve lo que pasó hoy.

Online

Rápido y con datos frescos, pero hay que calcular las variables al vuelo sin fuga: solo datos anteriores a la petición.

Los tres usan la misma versión del modelo y, mientras no llegan datos nuevos, dan la misma probabilidad para el mismo cliente y corte.
La demo lo hace visible: una compra simulada cambia la probabilidad online y no la del lote ni la de bajo demanda.

2 · Preparar el repositorio · paso 1, rama y workflows

Rama de trabajo y los cuatro workflows

Terminal del Codespace · en la raíz del repositorio
$ git switch develop
$ git pull
$ git switch -c lab/produccion-e2e
$ mkdir -p .github/workflows
$ cp 01-Sesiones/S4-Orquestacion-y-CI-CD/laboratorio-produccion-e2e/{puntuar-lote,validar-produccion,nueva-version,rollback}.yml .github/workflows/
$ git add .github/workflows
$ git commit -m "Laboratorio de cierre de S4: workflows de producción"
En un fork, antes: pestaña Actions y aceptar el aviso para activar los workflows. Aún no hagas push: primero se configura el repositorio.

Qué debes ver

  • On branch lab/produccion-e2e y .github/workflows/ con cuatro archivos nuevos.
  • Los cuatro: puntuar-lote.yml, validar-produccion.yml, nueva-version.yml y rollback.yml.
  • El cp copia los cuatro de una vez (llaves de bash); en otra terminal, cópialos uno a uno.

Si falla

  • cp: cannot stat …: tu fork no tiene la carpeta del laboratorio; haz Sync fork o copia cada YAML con «Copiar el archivo».
  • Sin Actions activado en el fork no aparecerá ningún run: pestaña Actions del fork.
  • El fork debe hacerse con «Copy the main branch only» desmarcado: si no, no tiene develop y fallan «Create codespace on develop» y git switch develop.
  • Un Codespace no se actualiza solo: git fetch origin, git status -sb (debe decir «behind N») y git pull origin develop.

Configurar el repositorio: environment y permiso de PR

A · El environment produccion

  1. Settings › Environments › New environment
  2. Nombre exacto: produccion (sin tilde; no prod)
  3. Marca Required reviewers y añádete a ti mismo
  4. Save protection rules

B · Permiso para abrir PR

  1. Settings › Actions › General › Workflow permissions
  2. Marca Allow GitHub Actions to create and approve pull requests
  3. Save
Sin A (o con otro nombre), la publicación no espera a nadie. Sin B, el último paso falla.

3 · Modo 1 · lote · cuándo y qué hace

Puntuación por lotes: todos los clientes, cada día

Cuándo se ejecuta

DisparadorDetalle
scheduletodos los días a las 05:17 UTC (cron: '17 5 * * *'); un minuto «raro» a propósito, porque a las horas en punto GitHub va cargado
workflow_dispatchRun workflow a mano, con tres entradas: capacidad (0.10 = el 10 %), corte e imagen (construir o ghcr)
push a lab/**solo si cambia el workflow o explotacion.py: así se prueba sin esperar al día siguiente
El push arranca dos runs: «Puntuar por lotes» (3 cajas) y «Validar la producción completa» (1 caja). No es un error. Si el push se rechaza con non-fast-forward, la rama ya existe en ese repositorio: no hagas git pull ni --force; renómbrala con git branch -m lab/produccion-e2e lab/produccion-e2e-2.
En un fork, el schedule viene desactivado. Se lanza con Run workflow; y Run workflow solo aparece si el workflow está en la rama por defecto: por eso en el laboratorio se dispara con el push.

Qué hace: tres trabajos

  • 1 · Preparar datos (operacional + pipeline).
  • 2 · Puntuar a todos los clientes: levanta la API en un contenedor y ejecuta explotacion --url.
  • 3 · Resumen: corte, clientes puntuados, campaña, probabilidad media, versión y huella del modelo.

Qué deja

  • Artefacto campana: campana_<corte>.csv y .json (todos los clientes, ordenados).
  • Artefacto base-fs-produccion: la base con la tabla fs_produccion (las 13 variables del corte), la que lee «bajo demanda».
Terminal · tras configurar el repositorio: este push lanza el lote y la validación
$ git push -u origin lab/produccion-e2e

5 · Una versión nueva · cómo se ensaya

El nombre de la rama elige el escenario

Rama de ensayo (lab/nueva-version/…)EscenarioResultado esperado
muestradatos de la muestra del repositorio (la fuente de la v1)IGUAL: misma huella; trabajos 2 a 4 omitidos
completo-rechazoExcel completo y tolerancia -0,10 (se exige mejorar 0,10)RECHAZADA: el trabajo 1 sale en rojo
completoExcel completo con la tolerancia por defecto (0,02)ACEPTADA: construye, espera aprobación, publica y abre el PR
Por qué ramas: Run workflow solo aparece si el workflow está en la rama por defecto. Un push a una rama lab/nueva-version/… lo lanza igual y el nombre decide los datos y la tolerancia. Hazlo en este orden: completo el último.
Terminal · una orden por escenario
$ git switch lab/produccion-e2e
$ git switch -c lab/nueva-version/muestra
$ git push -u origin lab/nueva-version/muestra
# cuando acabe: el rechazo
$ git switch lab/produccion-e2e && git switch -c lab/nueva-version/completo-rechazo
$ git push -u origin lab/nueva-version/completo-rechazo
# el último: el completo (espera aprobación)
$ git switch lab/produccion-e2e && git switch -c lab/nueva-version/completo
$ git push -u origin lab/nueva-version/completo

5 · Una versión nueva · el pipeline

Cuatro trabajos y una puerta de calidad

La puerta

Compara el AUC de test con el de models/referencia.json y una tolerancia de 0,02: misma huella → igual; el AUC cae más que la tolerancia → rechazada; en otro caso → aceptada.

La aprobación

El trabajo 3 usa el environment produccion: se queda esperando hasta que un revisor aprueba. Es el único con permiso para escribir paquetes.

«En producción» es…

la imagen retencion-api:v<N>-<huella> en GHCR más referencia.json y historial_versiones.json (la pestaña Versiones). Pasa a ser la de producción al fusionar el PR.

5 · Una versión nueva · la v2 pasa a ser la de producción

Fusionar el PR: ahora sí es la de producción

Fusionar

  1. Abre el PR nº 2 (pestaña Pull requests)
  2. Revisa Files changed: dos archivos
  3. Merge pull request
  4. Confirm merge
Hasta fusionar, la v2 existe en GHCR pero no está en producción: la ficha sigue diciendo v1. El siguiente lote usará la v2 cuando el PR esté fusionado.

Qué no hace

  • No empuja a develop ni a main: aquí el PR va contra la rama de ensayo.
  • Un PR creado con el GITHUB_TOKEN no lanza otros workflows (regla de GitHub).

6 · Volver atrás · cómo se lanza

Lanzar el rollback desde una rama con la v2 fusionada

Terminal · tras fusionar el PR nº 2
$ git fetch origin
$ git switch lab/nueva-version/completo
$ git pull
# 1) con comprobación: se parará, a propósito
$ git switch -c lab/rollback/v1
$ git push -u origin lab/rollback/v1
# 2) sin comprobar la imagen: abre el PR
$ git switch -c lab/rollback/v1-sin-comprobar
$ git push -u origin lab/rollback/v1-sin-comprobar

Cómo funciona

  • El rollback no reentrena ni reconstruye: busca en el historial de git la ficha de la versión pedida (por defecto, la anterior a la actual).
  • Por defecto comprueba que su imagen exista en GHCR; con «sin-comprobar» en el nombre de la rama, no.
  • Abre un PR y no borra nada.

Si falla

  • El run no arranca: puede haber otro run del grupo nueva-version-modelo esperando aprobación; cancélalo o apruébalo.
  • Hay que salir de una rama que ya tenga la v2 fusionada: si no, no hay una versión anterior que restaurar.

6 · Volver atrás · lo que cambia

El PR nº 3 restaura la ficha y no borra nada

Qué hace

  • Restaura referencia.json tal cual estaba en el commit anterior (la v1).
  • En el historial: la v1 vuelve a produccion y la v2 pasa a retirada.
  • Al fusionarlo, el siguiente lote vuelve a usar la imagen de la v1.

Qué no hace

  • No se borra nada: la imagen de la v2 sigue en GHCR y el historial se conserva.
  • Volver a avanzar es lanzar «Nueva versión del modelo» otra vez.
  • Alternativa: el botón Revert del PR de referencia que se fusionó.

7 · Problemas y cierre · Comprueba que lo tienes

Seis preguntas

1. ¿Qué modo usarías para la campaña de cada mañana y cuál para una compra que acaba de ocurrir?

Lote para la campaña (puntúa a todos); online para lo que acaba de ocurrir (variables calculadas al vuelo).

2. ¿Por qué «bajo demanda» no cambia tras la compra simulada?

Lee las variables ya calculadas de fs_produccion, las de ayer; solo online las recalcula.

3. ¿Qué decide la puerta de calidad?

Compara el AUC de test con referencia.json y la tolerancia: igual, rechazada o aceptada.

4. ¿Qué hace el environment produccion?

Obliga a que un revisor apruebe antes de publicar en GHCR.

5. ¿Por qué el primer rollback se para y qué no borra ninguno?

La imagen de la v1 nunca se publicó. Ninguno borra imágenes ni el historial: se restaura la ficha.

6. ¿Dónde ves qué versión está en producción?

En models/referencia.json (y su historial) y en la pestaña Versiones del panel.

7 · Problemas y cierre · El mensaje

Producción no es subir un modelo: es poder cambiarlo con control y volver atrás
