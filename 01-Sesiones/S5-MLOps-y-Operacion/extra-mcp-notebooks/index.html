Construyes dos servidores MCP sin salir de un notebook: uno que consulta la capa master del caso Retail (en SQLite y en BigQuery) y otro que lleva dentro el modelo de retención a 90 días. Y los vigilas: lo que importa de un MCP no es que funcione, sino que no pueda hacer daño.

2 · Un MCP que consulta los datos · diseño de mcp-datos-master

Un LLM que escribe SQL es peligroso: cuatro capas, y las dos últimas no dependen de nadie

Las capas

  • 1 · herramientas con nombre y argumentos tipados: el SQL lo escribes tú.
  • 2 · consulta_sql es el último recurso y la vigila validar_sql.
  • 3 · SQLite se abre en mode=ro; BigQuery lleva un tope de bytes (maximum_bytes_billed).
  • 4 · nunca se devuelven más de 50 filas.
Las capas 3 y 4 no dependen del LLM ni de la capa 2: si la vigilancia falla, siguen protegiendo. Por eso validar_sql puede ser una expresión regular sin que sea «la» defensa.

2 · Un MCP que consulta los datos · SQLite y BigQuery

Dos conectores con la misma interfaz: el servidor no sabe qué motor hay detrás

ConectorSQLite · extracto del notebook 01 (sin comentarios)
    def _abrir(self):
        con = sqlite3.connect(self.ruta.resolve().as_uri() + '?mode=ro', uri=True)
        con.row_factory = sqlite3.Row
        return con

    def ejecutar(self, sql, params=None):
        con = self._abrir()
        try:
            filas = [dict(f) for f in con.execute(sql, params or {}).fetchmany(MAX_FILAS + 1)]
        finally:
            con.close()
        return [{k: _limpio(v) for k, v in f.items()} for f in filas]
ConectorBigQuery · extracto del notebook 01 (sin comentarios)
    def ejecutar(self, sql, params=None):
        tipos = {bool: 'BOOL', int: 'INT64', float: 'FLOAT64', str: 'STRING'}
        parametros = [self.bq.ScalarQueryParameter(k, tipos[type(v)], v) for k, v in (params or {}).items()]
        config = self.bq.QueryJobConfig(query_parameters=parametros, maximum_bytes_billed=MAX_BYTES_BQ)
        job = self.cliente.query(sql, job_config=config)
        return [{k: _limpio(v) for k, v in dict(f.items()).items()} for f in job.result(max_results=MAX_FILAS + 1)]

La interfaz

  • Los dos ofrecen tabla(), columnas() y ejecutar().
  • Las consultas usan parámetros @nombre: valen para los dos motores.

Cómo se elige

  • Una variable de entorno: MCP_BACKEND=sqlite (por defecto) o bigquery.
  • Con BigQuery hacen falta GCP_PROJECT y, si no es curso_master, BQ_DATASET.

Lo que cambia por motor

  • SQLite: abre la base en solo lectura (capa 3).
  • BigQuery: un tope de 100 MB por consulta (MCP_BQ_MAX_BYTES); el dataset entero pesa unos 2 MB.

2 · Un MCP que consulta los datos · lo que hace VS Code, en un notebook

Un cliente MCP son treinta líneas: lanza el servidor y le habla por stdio

ClienteMCP · notebook 01, apartado 2 (sin docstring ni comentarios)
class ClienteMCP:
    def __init__(self, script, **entorno):
        self.params = StdioServerParameters(command=sys.executable, args=[str(script)], env={**os.environ, **{k: str(v) for k, v in entorno.items()}})

    async def __aenter__(self):
        self._pila = AsyncExitStack()
        self._log = open(TRABAJO / 'servidor.err', 'w', encoding='utf-8')
        leer, escribir = await self._pila.enter_async_context(stdio_client(self.params, errlog=self._log))
        self.sesion = await self._pila.enter_async_context(ClientSession(leer, escribir))
        await self.sesion.initialize()
        return self

    async def __aexit__(self, *a):
        await self._pila.aclose()
        self._log.close()

    async def herramientas(self):
        return (await self.sesion.list_tools()).tools

    async def llamar(self, nombre, **argumentos):
        r = await self.sesion.call_tool(nombre, argumentos)
        if r.isError:
            return {'error_del_protocolo': r.content[0].text}
        return r.structuredContent or json.loads(r.content[0].text)

Qué debes ver

  • El cliente lanza el servidor como proceso hijo y le habla por su entrada y salida estándar (transporte stdio).
  • herramientas() pide la lista y llamar(nombre, **args) ejecuta una.
  • Si el propio protocolo rechaza los argumentos (un tipo mal puesto), isError lo recoge como error_del_protocolo.
Ojo en Jupyter: stdio_client escribe el stderr del servidor en sys.stderr, y el de Jupyter no tiene fileno. Por eso se abre un archivo (servidor.err) y se pasa como errlog.
Y un servidor nunca debe usar print hacia la salida estándar: stdout es el canal del protocolo. Los avisos van por stderr.

El tope de coste funciona: con 1 byte, BigQuery ni ejecuta la consulta

Qué debes ver

  • El tope se fija con MCP_BQ_MAX_BYTES; la prueba lo baja a 1 byte y BigQuery responde «Query exceeded limit for bytes billed: 1. 20971520 or higher required».

4 · Un MCP con el modelo dentro · qué modelo responde

No carga un archivo: pregunta al alias @champion en cada llamada

modelo_champion() · notebook 02, apartado 2 (sin comentarios)
def modelo_champion():
    """(modelo, versión, métricas) de lo que apunte el alias AHORA. Solo recarga si la versión cambió."""
    c = _cliente_mlflow()
    try:
        mv = c.get_model_version_by_alias(config.MODELO_REGISTRADO, ALIAS)
    except Exception as e:
        raise LookupError(f'«{config.MODELO_REGISTRADO}» no tiene el alias @{ALIAS}: asígnalo (python -m ia_mlops.alias_modelo promover --version N)') from e
    version = int(mv.version)
    if _cache['version'] != version:
        import mlflow.sklearn
        _cache.update(version=version, modelo=mlflow.sklearn.load_model(f'models:/{config.MODELO_REGISTRADO}/{version}'),
                      metricas=c.get_run(mv.run_id).data.metrics if mv.run_id else {})
    return _cache['modelo'], version, _cache['metricas']

Qué debes ver

  • En cada llamada pregunta a MLflow a qué versión apunta models:/retencion-90d@champion.
  • Solo recarga si la versión cambió (la carga es lo caro).
  • Si el alias no existe, devuelve un error claro con la orden para asignarlo, no un traceback.
Así un rollback (mover el alias) cambia lo que responde el MCP sin reiniciarlo y sin tocar el código. Es la parte MLOps: lo que manda es el registro, no un archivo.

4 · Un MCP con el modelo dentro · por_que(12369)

Por qué sale 0,3035: el modelo es una regresión logística y se reparte exacto

Salida guardada · notebook 02 · apartado 5
--- ¿por qué?
  frecuencia_180d    valor 0        peso -1.339  → baja la probabilidad
  recencia_dias      valor 413      peso +0.583  → sube la probabilidad
  devoluciones       valor 0        peso -0.516  → baja la probabilidad
  es_reino_unido     valor 0        peso +0.390  → sube la probabilidad
  intercepto +0.225  logit total -0.831  →  probabilidad 0.3035

Fuente: notebook 02, apartado 5 (por_que con n=4).

Qué debes ver

  • Cada peso es coeficiente × valor transformado; intercepto +0,225 más la suma de todos los pesos = logit −0,831.
  • La probabilidad es 1/(1+e^-logit) = 0,3035: la descomposición reproduce la cifra del modelo.
  • Sin actividad en 180 días baja (−1,339); devoluciones 0 baja (−0,516).
Dice qué empuja la cifra, no por qué compra el cliente. Y fíjate: 413 días sin comprar sube (+0,583). Eso se explora en la siguiente diapositiva.

Sin verificar que el reparto exacto valga para otro modelo: si no es una regresión logística, la herramienta devuelve una nota y no reparte.
