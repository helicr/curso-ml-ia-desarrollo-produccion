La idea clave de S2

Un archivo en disco no es un servicio

La API

FastAPI carga el modelo y responde por HTTP. /predecir para un cliente, /predecir/lote para hasta 1 000.

La imagen

Python, paquetes con versiones exactas, código y modelo. Se construye una vez y se ejecuta donde se quiera.

El control

Un workflow de GitHub Actions reproduce el pipeline, pasa las pruebas, construye la imagen y la prueba.

Las 13 variables de la capa FS son la entrada: un cliente en una fecha de corte, igual que en S1.

Recap 022
El contrato

El contrato no se escribe dos veces: viaja con el modelo

Si no coincide: 503 con el motivo

/listo y /predecir responden 503 y nombran los campos que faltan o sobran. Es mejor fallar al desplegar que dar probabilidades con columnas cambiadas.

Por qué no joblib solo

Con joblib el contrato viviría fuera del modelo y podría desincronizarse. En formato MLflow viaja con él.

La tarea de S2 lo provoca: reentrenar con una variable nueva y no actualizar esquemas.py da un 503, no un 500. Las pruebas comprueban que el esquema coincide con la firma, y el límite de cada campo sale de cómo se construye FS, no de lo visto al entrenar.

Recap 024
Operar el servicio

Vivo no es lo mismo que listo

/salud · ¿estás vivo?

¿El proceso responde? No mira el modelo. Si no responde, el orquestador lo reinicia.

200 {"estado":"ok"}

/listo · ¿puedes atender?

¿El modelo está cargado y coincide con su contrato? Si no, reiniciar no sirve: hay que arreglar lo que falta.

200, o 503 con el motivo

Un servicio sin modelo arrancó (vivo) y no está listo. El orquestador usa /salud para reiniciar y /listo para decidir si envía tráfico.

Los registros: una línea JSON por petición

# salida estándar del servicio: una línea por petición (aquí partida para leerla) {"severity": "INFO", "message": "POST /predecir 200", "evento": "peticion", "id": "26ac527aa211", "metodo": "POST", "ruta": "/predecir", "codigo": 200, "ms": 45.6}

severity y message son los campos que Cloud Logging reconoce.

X-Request-ID une lo que vio quien llamó con el registro. En un 500, el traceback va al registro con ese id.

Nunca se registran los datos del cliente: solo método, ruta, código, duración e id.

Recap 026
Imagen frente a contenedor

Una imagen, muchos contenedores

Puerto

-p equipo:contenedor abre una puerta. Dentro del contenedor el servidor escucha en 0.0.0.0; 127.0.0.1 allí es el propio contenedor.

Volumen

-v origen:destino:ro monta una carpeta del equipo. Los datos quedan fuera de la imagen y, con :ro, no se pueden modificar.

Variables de entorno

-e o ENV: la configuración llega desde fuera. El mismo código sirve en cualquier sitio.

$ docker build -f deploy/docker/Dockerfile --build-arg FUENTE=contexto --build-context modelo=models -t retencion-api:local .
$ docker run --rm -p 8080:8080 retencion-api:local
Recap 027
Comparar caminos · muestra del curso

Si es el mismo modelo, la misma probabilidad

826 MB

Tamaño de la imagen en disco, construida en GitHub Actions; 183 MB de «contenido» en docker image ls. Pesan pandas, scipy y scikit-learn.

Usuario 10001

docker exec … id -u da 10001: no corre como root. Si alguien explota la API, no es administrador del contenedor.

Diferencia 0

python -m ia_mlops.modeling.comparar: con 200 filas de test, la diferencia máxima entre caminos fue 0.000e+00. Salida 0 = todo coincide.

Valor completo: 0.8278889191932133, igual en local y en el contenedor. Otro sistema operativo puede cambiar los últimos decimales.

GitHub Actions y el taller

Cada cambio se prueba solo

El primer workflow (ci.yml)

  1. Instala las dependencias de requirements-dev.txt
  2. Ejecuta el pipeline completo
  3. Pasa las pruebas
  4. Construye la imagen
  5. Arranca el contenedor: /listo, /modelo, una predicción y un 422 por campo fuera del contrato
  6. Si algo falla, muestra el registro del contenedor

En cada push y pull_request a develop o main. Permisos contents: read, sin secretos y sin publicar nada: eso es S4.

Autoevaluación · pulsa cada pregunta

¿Lo tienes? Seis preguntas

Reentrenas con una variable nueva y no tocas la API. ¿Qué responde?
503, no 500: la firma del modelo no coincide con el esquema y /listo nombra la variable que falta. El servicio sigue vivo.
Llega recencia_dias = -1. ¿Qué código y quién actúa?
422, y actúa quien llama: el valor es imposible. Rechazar evita un error dentro de scikit-learn o una probabilidad sin sentido.
Un cliente con un ticket medio nunca visto al entrenar. ¿Rechazar o avisar?
Avisar: 200 con advertencias. Es posible pero sin respaldo; rechazarlo dejaría sin predicción a un cliente real.
¿Por qué las dependencias van antes que el código en el Dockerfile?
Por la caché de capas: la de dependencias solo se reconstruye si cambia requirements-api.lock. Una línea de código no reinstala todo.
La interfaz llama a http://api:8080, no a 127.0.0.1. ¿Por qué?
Dentro de un contenedor, 127.0.0.1 es el propio contenedor. En la red retencion, Docker resuelve el nombre api.
La API se cae. ¿Qué dicen /salud y /listo de la interfaz?
/salud 200 y /listo 503. Por eso el HEALTHCHECK mira /salud: reiniciar la interfaz no arregla la API.

Recap 0212
Lo que viene en S3

El código no cambia: cambia dónde corre

Lo que se queda igual

  • La imagen que construiste en S2 (es la que se despliega)
  • El contrato, que sale de la firma del modelo
  • Los códigos 200, 422, 503 y 500
  • /salud y /listo
  • El registro JSON por stdout (severity y message ya son los campos de Cloud Logging)

Lo que cambia

  • Quién ejecuta el contenedor: una plataforma gestionada, no tu sesión
  • De dónde sale la imagen: un registro, no tu equipo
  • Quién puede llamar: usuarios y servicios autenticados
  • Dónde viven los datos y los secretos
  • Qué se mide y qué cuesta: presupuesto, alertas y borrar al terminar
Una precisión de S2: la API lleva el modelo dentro y no lee datos; quien lee datos es la interfaz, con la base en un volumen de solo lectura. Lo que no se haya ejecutado de verdad en GCP se marcará «sin verificar». Publicar desde el workflow es S4; vigilar el modelo, S5.
