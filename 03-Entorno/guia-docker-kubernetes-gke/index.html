A · Conceptos · Kubernetes

Con docker run tienes un contenedor.
En producción necesitas a alguien que lo vigile

Se cae

El proceso muere a las 3 de la madrugada. Con Docker solo, sigue caído hasta que alguien lo vea.

Kubernetes: crea otro pod en segundos (paso 6 de la práctica).

Llega más carga

Una campaña dispara las peticiones. Un contenedor no da abasto.

Kubernetes: replicas: 3 y el Service reparte (paso 7).

Hay que actualizar

Nuevo modelo. Parar el viejo y arrancar el nuevo deja un hueco, y si el nuevo falla, todo cae.

Kubernetes: sustituye poco a poco; si el nuevo no está listo, el viejo sigue sirviendo (pasos 8 y 9).

Kubernetes es un orquestador: le dices qué quieres («2 copias de esta imagen, sin root, que respondan en /listo») y él se encarga de que siga siendo así.

A · Conceptos · el archivo real

04-Proyecto-Base/deploy/kubernetes/deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata: { name: retencion-api, labels: { app: retencion-api } }
spec:
  replicas: 2                                         # (1)
  selector: { matchLabels: { app: retencion-api } }   # (2)
  template:
    metadata: { labels: { app: retencion-api } }
    spec:
      securityContext: { runAsNonRoot: true, runAsUser: 10001 }   # (3)
      containers:
        - name: api
          image: retencion-api:local
          imagePullPolicy: IfNotPresent                 # (4)
          ports: [ { containerPort: 8080 } ]
          readinessProbe: { httpGet: { path: /listo, port: 8080 } }   # (5)
          livenessProbe:  { httpGet: { path: /salud, port: 8080 } }   # (6)
          resources:
            requests: { cpu: 100m, memory: 256Mi }      # (7)
            limits:   { memory: 1Gi }
  • (1) Kubernetes mantiene 2 pods siempre.
  • (2) Deployment, pods y Service se encuentran por la etiqueta app: retencion-api.
  • (3) Igual que el USER 10001 del Dockerfile; si la imagen intentara ser root, no arrancaría.
  • (4) En kind la imagen se carga con kind load; no hay que descargarla.
  • (5) readiness: ¿puede recibir tráfico? Mientras /listo no dé 200, el Service no le manda peticiones.
  • (6) liveness: ¿sigue vivo? Si /salud deja de responder, se reinicia el contenedor.
  • (7) Recursos: lo que reserva (requests) y el techo de memoria (limits).

Versión recortada (las llaves son YAML válido). El archivo completo lleva además los tiempos de las probes y una variable de entorno.

Las dos preguntas que Kubernetes hace sin parar

Readiness · /listo

«¿Puedes atender peticiones?» Si responde 503 (sin modelo, contrato roto) o falla, el pod sigue vivo pero sale del Service: no recibe tráfico hasta que vuelva a estar listo.

Se ve como Running 0/1 y en kubectl get endpoints falta su IP.

Liveness · /salud

«¿Sigues vivo?» Si deja de responder, Kubernetes reinicia el contenedor (sube RESTARTS). Si se reinicia una y otra vez: CrashLoopBackOff.

Por eso /salud no mira el modelo: solo que el proceso responde.

2 Darle la imagen al clúster

De kind a GKE: qué comandos cambian

# 1. Repositorio de imágenes y permisos de Docker
gcloud artifacts repositories create curso-repo --repository-format=docker --location=us-central1 --description="Imágenes del curso"
gcloud auth configure-docker us-central1-docker.pkg.dev

# 2. Subir la imagen (en vez de kind load)
docker tag retencion-api:local us-central1-docker.pkg.dev/PROYECTO/curso-repo/retencion-api:v1
docker push us-central1-docker.pkg.dev/PROYECTO/curso-repo/retencion-api:v1
# 3. Clúster Autopilot y kubectl apuntando a él
gcloud container clusters create-auto curso-gke --location=us-central1
gcloud container clusters get-credentials curso-gke --location us-central1

# 4. Desplegar: mismos YAML, cambiando image: por la ruta
#    de Artifact Registry y el Service a type: LoadBalancer
kubectl apply -f deploy/kubernetes/
kubectl get service retencion-api      # EXTERNAL-IP

# 5. Borrar (¡imprescindible!)
gcloud container clusters delete curso-gke --location us-central1
gcloud artifacts repositories delete curso-repo --location=us-central1

Sustituye PROYECTO por el id de tu proyecto. En el YAML, imagePullPolicy: IfNotPresent puede quedarse; lo que cambia es image:. Fuentes al final.

C · GKE Antes de crear nada

Antes de crear un clúster de verdad

Cuesta mientras exista

Autopilot cobra por los recursos que piden los pods; Standard, por los nodos. El balanceador también se paga. Calcúlalo antes en la calculadora de Google Cloud y pon una alerta de presupuesto.

IP pública = API expuesta

Nuestra API no tiene autenticación. Con type: LoadBalancer cualquiera con la IP puede llamarla. Para el curso, Cloud Run (S3) con acceso restringido es más sencillo.

Permisos mínimos

Para empujar imágenes y desplegar hacen falta roles de Artifact Registry y de GKE. Desde GitHub Actions, sin claves en el repositorio: Workload Identity Federation (S4).

En este curso no se crea ningún clúster de GKE. Todo lo de Kubernetes se practica con kind, que habla la misma API: lo que aprendes con kubectl vale tal cual.

Ahora tú: seis ejercicios

1 · Leer

¿Qué nodo e IP tiene cada pod? ¿Qué etiqueta une el Service con los pods? (get pods -o wide, describe service)

2 · Escalar de forma declarativa

Pasa a 3 réplicas editando el YAML, aplica y comprueba. ¿Qué diferencia hay con kubectl scale?

3 · Olvidar kind load

Construye retencion-api:v2, cambia el YAML a esa etiqueta y aplica sin cargarla. ¿Qué estado ves y qué dice el evento? Arréglalo.

4 · Sin modelo

Despliega la imagen de S2 sin modelo (o una ruta de modelo errónea por variable de entorno). ¿El pod está vivo? ¿Está listo? ¿Por qué esa diferencia es la que queremos?

5 · Límite de memoria

Baja limits.memory a 64Mi y aplica. ¿Qué pasa? Busca la palabra clave en describe pod.

6 · Llevarlo a GKE (en papel)

Escribe los cambios del YAML y la lista de comandos para desplegarlo en GKE. ¿Qué borrarías al acabar y en qué orden?
